# Per-jurisdiction setback tables

Hand-curated JSON tables (locked decision #9 / DA-PI-4) populated from
publicly available ordinances. One file per jurisdiction; one row per
zoning district.

## Schema

```json
{
  "district_name": "string",
  "front_ft": "number",
  "rear_ft": "number",
  "side_ft": "number",
  "side_corner_ft": "number",
  "max_height_ft": "number",
  "max_lot_coverage_pct": "number",
  "max_impervious_pct": "number",
  "citation_url": "string"
}
```

## Why hand-curated rather than scraped from the GIS layer?

The GIS layer carries the polygon and the district code, but the
dimensional rules live in the ordinance text — typically a PDF that
isn't reliably structured. Code-ontology ingestion (zoning ordinances
→ `code-section` atoms) is explicitly out of scope for this sprint per
Spec 51 OQ-1, so the table is the bridge between the polygon and the
prose-only ordinance until the A05 code-atom pipeline ships.

## Adding a jurisdiction

1. Drop a `<jurisdiction-key>.json` file here (use the same slug the
   adapter writes to `briefing_sources.provider`).
2. Append the import + record entry in `index.ts`.
3. Adjust the test asserting completeness in `__tests__/`.

## Acceptance gate (new / fan-out tables)

New tables added by the multi-jurisdiction extraction fan-out MUST carry a
per-value `provenance` block and pass the setback extraction acceptance gate
before their `districts[]` is populated. The gate spec is
`docs/setback-extraction-acceptance-gate.md`; the executable checker is
`gate.ts` (exported as `@workspace/adapters/setbacks/gate`,
`runSetbackGate`). It takes the extracted table plus the jurisdiction's source
code-section atoms and returns pass / flag / block per rule per value:
uncited or fabricated citations, missing districts, and missing verification
state BLOCK; out-of-band values and asserted-quote mismatches FLAG for human
review. The serving route ignores `provenance` — it never reaches the wire —
so adding it cannot change the FE contract.

The four legacy hand-curated tables (Grand County, Lemhi, Bastrop, and the two
statewide fallbacks) predate the gate and carry no `provenance`; the gate
treats them as un-gated legacy tables (reported, not silently passed).
`san-marcos-tx.json` is registered with an empty `districts[]` because San
Marcos is not yet in the code atom corpus — it serves 200 with a pending note
rather than 404, and no setback values ship until citation-backed extraction
plus human review land.

## Statewide fallback tables

Two tables are statewide fallbacks rather than per-county entries:
`utah-unincorporated.json` and `idaho-unincorporated.json`. They serve
parcels whose `localKey` resolves to a county we don't have a
hand-curated table for, but whose state has reasonably uniform
unincorporated zoning rules at the state level.

Decision (DA-PI-4 / V1-5, 2026-05-02): keep these as discovered
implementation detail rather than promoting them to a first-class
"statewide fallback" concept in the spec docs. The fallback rows already
carry honest per-row provenance and the adapter output labels them
clearly, so a spec-level concept would add doc surface without
changing behaviour. Revisit if a third statewide-fallback table appears —
at that point the pattern is worth naming.

### Why no `texas-unincorporated` table

Decision (DA-PI-4 / V1-5, 2026-05-02): intentional skip. Texas
unincorporated zoning is effectively non-existent at the state level —
counties have no zoning authority absent a special charter — so a
statewide fallback table would produce more confusion than signal. A
Texas parcel that resolves to an unincorporated localKey gets no setback
row from this directory, which is the correct answer rather than a
misleading default.

## Burnet: Marble Falls and Horseshoe Bay (pack E, 2026-10-13)

Both cities' register rows and the `marble-falls-tx.json` table are generated by
`lib/adapters/scripts/apply-packE-to-burnet-register.mjs` from
`doc_repo/_inbox/2026-10-13_burnet_B3_groundtruth_browser_packE.csv` (official
hosts only: Municode for Marble Falls, eCode360 Ch. 14 Art. 14.02 for Horseshoe
Bay). Edit the script's reviewed tables and re-run it; do not hand-edit those rows.

**Marble Falls: one row per building type.** Its tables give one row per building
type (Single-Family Detached, Duplex, Apartment ...), not one per district, and
mark none as primary. The serving path resolves by district only, so a district is
served only when its table gives it exactly one Single-Family Detached row (or only
one row at all); every other row is quoted in the register. The rest refuse
`SETBACK_CONDITIONAL_NOT_EVALUATED` with a `conditional_reason`.

**Horseshoe Bay is keyed by geographic zone.** The same district code carries
different standards in different geographic zones (§§ 14.02.404-.422), and no
parcel's zone is resolved yet, so every stamped code whose standards vary by zone
refuses `SETBACK_CONDITIONAL_NOT_EVALUATED` ("standards vary by Horseshoe Bay
geographic zone; parcel zone not resolved"). The per-(code, zone) standards live in
`horseshoe-bay-tx-zone-standards.json`, which is deliberately NOT a
`SETBACK_TABLES` entry; its `zone_resolution_spec` says how a parcel's zone can be
resolved from the zoning layer's `SUBDIVISION` attribute when that is built. No
`horseshoe-bay-tx` table is vendored: no stamped code serves, and the three codes
the register clears (R-6.5, R-16, M-1; none on a Burnet parcel) refuse
`SETBACK_TABLE_ABSENT`, because R-16 / R-6.5 would be prefix-neighbours of the
stamped, refused R-1 / R-6 in `districtMapping.ts`'s prefix fallback.

## Burnet: per-parcel resolution for Marble Falls and Horseshoe Bay (2026-10-13)

Operator ruling: "don't ship Burnet half way; do the districts". The districts above
that refuse by district code now resolve PER PARCEL in `burnet-parcel-setbacks.ts`
(package export `@workspace/adapters/setbacks/burnet-parcel`,
`resolveBurnetParcelSetbacks`). By district code alone `getSetbackTableForZoning`
still refuses them, correctly: the condition needs the parcel.

Data: `burnet-parcel-standards.json`, generated by
`lib/adapters/scripts/build-burnet-parcel-standards.mjs <packE.csv>` (do not hand-edit;
every row is named in that script's reviewed tables, and an unexpected pack E row
throws). Lakes: `water/nhd-lake-marble-falls.json` and `water/nhd-lake-lbj.json`,
USGS NHD High Resolution waterbodies vendored by `scripts/vendor-nhd-lakes.mjs`.

Outcomes, never a guessed number:

- `SETBACK_PARCEL_SERVED`: the parcel's data settles every condition and all four
  setbacks are single numbers.
- `SETBACK_CONDITIONAL_SET`: the ordinance's standards as branches ("if X: a; if Y: b"),
  or a setback the ordinance states as a rule (a total side yard, an
  abutting-residential rule, a build-to line). A caller that can only show four
  numbers must decline with this code.
- A named decline: `SETBACK_SOURCE_PENDING` (text not sourced yet; pack F),
  `SETBACK_ZONE_UNRESOLVED` (no `txgio_parcel.zoning_subarea`),
  `SETBACK_ZONE_UNMAPPED` (a SUBDIVISION value not in the reviewed map, e.g. WEST),
  `SETBACK_ZONE_COMBINATION_UNTABLED`, or the register's own code.

Facts evaluated (`burnet-parcel-facts.ts`):

- Horseshoe Bay zone: the zoning layer's `SUBDIVISION`, written by the zoning stamp to
  `txgio_parcel.zoning_subarea` (migration 0113), mapped by an explicit table (14
  name matches; SOUTH = Zone 4B; PROPER = Zones 3/4A, inferred and served only where
  § 14.02.406 gives 3 and 4A one text; WEST unmapped).
- Lake adjacency (Marble Falls Table 4.3.1.B note 1, Lake Marble Falls; Horseshoe Bay
  waterfront rear and shoreline height, Lake LBJ): intersects the NHD polygon =
  adjacent; 60 m or more away = not adjacent; in between = undetermined (both
  branches served).
- Lot width (Marble Falls Table 4.2.6.A, DR): for a near-rectangular lot, bounded by
  the bounding rectangle's short and long sides (plus or minus 1 ft); a row is kept if
  its width band can hold that interval.
- CAD category (PTAD letter of `cad_property.property_use_code`): F narrows a district
  to its Table 4.3.1.B nonresidential row; A/B/M set that row aside in FR/RE/NR/TR/MR/DR.

Plat clause (operator ruling 2026-10-13): where a Horseshoe Bay yard paragraph opens
"Except as specified to the contrary on an approved plat", the default is served with
`platNote` ("A recorded plat may set different setbacks."), never silently.
